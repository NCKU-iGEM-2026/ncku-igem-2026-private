CAPTURE-Screen, the fluorescence reader described on our Hardware page, reads sfGFP through an AS7341 spectral sensor. The instrument sits on a lab bench; this page lets anyone watch what its sensor sees, as it sees it.

The panel below is part of LasReader, the software we wrote to run the instrument. It shows the sensor's raw output, frame by frame, straight from the device. Nothing in it is simulated: when CAPTURE-Screen is switched off, the panel says so and shows no data.

Reading the panel

The AS7341 splits incoming light into ten channels. Eight are narrow bands across the visible spectrum, from F1 (415 nm) to F8 (680 nm); the other two are a broadband Clear channel and a near-infrared (NIR) channel. Each bar is one channel's reading in the latest frame.

F4 (515 nm) is the band that covers sfGFP emission, so it is the one bar drawn in green and the one number called out above the chart. For comparison, the wet lab reads sfGFP on a plate reader at an emission wavelength of 510 nm.

Status
Connecting: this page is still reaching our backend. Offline: the backend is up, but CAPTURE-Screen is not connected. Online: the device is ready. Streaming: frames are arriving.
Live
Turns on the excitation LED and starts the stream. Off by default.
Raw counts
The sensor's ADC output for each channel, before any processing.
Gain, Integration
The sensor settings the counts were taken with. The same light gives different counts at a different gain or integration time, so raw counts cannot be interpreted without them.
Full scale
The highest count a channel can report at the current integration settings: (ATIME + 1) × (ASTEP + 1), capped at 65,535. A bar near full scale is close to saturating.
LED
The excitation LED's drive current, measured with a multimeter, since the firmware cannot read it.
Build, Firmware, Wi-Fi
Which physical unit and firmware version is sending the data, and its Wi-Fi signal strength.

  1. When CAPTURE-Screen powers on and joins Wi-Fi, its ESP32 opens a WebSocket to our backend and keeps it open, reconnecting on its own if it drops. It reports its status every 5 seconds; if the backend hears nothing for 15 seconds, it marks the device offline.
  2. This page opens its own WebSocket to the backend as soon as it loads, so it can show whether the device is online before anyone asks for data.
  3. Switching on Live tells the backend that one more person is watching. When the first viewer arrives, the backend tells the device to turn on the LED and start streaming.
  4. The device reads all ten channels and sends each frame to the backend, which forwards it to every browser that is watching.
  5. When the last viewer switches Live off or closes the page, the backend tells the device to stop, and the LED goes off.

Design choices

The device connects out, not in

The backend runs in the cloud, and a lab or home router does not let the cloud reach a device behind it. So the direction is reversed: CAPTURE-Screen dials out to the backend, and browsers talk only to the backend. The device never needs a public address.

The LED is on only while someone is watching

Continuous excitation light warms the sample in the cuvette and photobleaches it. So the LED follows viewers, not the page: it lights when the first person switches on Live and turns off when the last one leaves. Moving this tab to the background counts as leaving, because nobody can see a hidden tab; the stream resumes when the tab comes back. If the device loses its connection to the backend, the firmware turns the LED off by itself.

Live data is shown, never kept

A live frame is a single reading with no dark subtraction. That is enough to watch the sensor respond, but it is not a measurement. LasReader therefore only draws live frames and never stores them, so they cannot end up in a calibration or a result. Recorded measurements take a separate path, with a dark reading before and after the lit one.

An old frame never looks current

When the device goes offline or the connection drops, the chart is cleared instead of left showing the last frame. While the device is busy with a measurement, which pauses the stream, the last frame is faded.

Nothing loaded from outside iGEM

The standalone LasReader site draws this chart with Chart.js. The wiki may not load scripts from external servers, so for this page we redrew the bar chart as plain SVG, with no third-party library.

Limitations

  • No authentication yet. Anyone who knows the backend address could pose as the device or ask it for a reading. We plan to add a shared secret between the device and the backend.
  • Slow first connection. The backend runs on a free hosting tier that sleeps when idle. The first visitor after a quiet period can wait up to a minute; the page and the device both keep retrying on their own.
  • One device, one server process. The backend keeps its connections in memory, which works for a single CAPTURE-Screen and a single server process. Scaling beyond that would need changes, such as a shared message broker.
  • Only while the device is on. The panel shows real data only; when CAPTURE-Screen is switched off, it shows the device as offline.
